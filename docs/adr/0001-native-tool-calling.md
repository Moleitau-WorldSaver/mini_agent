# 采用原生工具调用，而非手写文本协议

状态：已接受（2026-11-24）

Runtime 需要从模型输出中提取思考内容、工具调用与最终答案。我们选择使用 DeepSeek 的原生 function calling（`tools` + 结构化 `tool_calls`），而不是让模型输出 `<tool>{...}</tool>` 之类的自定义文本、再由 Runtime 写容错解析器：MVP 的首要目标是可靠，原生协议把格式正确性交给模型 API，Runtime 只负责分类提取。`ModelAdapter` 接口保留扩展缝，将来若要支持文本协议，可新增一个实现而无需改动 loop。

**考虑过的选项**

- 自定义文本协议：更能展示手写解析能力，但格式错误、半截 JSON、模型不守约定会成为常态，与"最小可用"冲突。
- 双模式并行实现：工作量约增 30%，MVP 不需要。

**后果**

- 行为受 provider 协议约束：并发工具调用不可关闭，思考模式下 `tool_choice` 仅支持 `none`/`auto`。
- 仍需防御 `arguments` 不是合法 JSON 的情况，按工具错误处理并计入 Step。
